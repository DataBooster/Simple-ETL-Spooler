# Simple ETL Spooler

<p align="right"><a href="README.md">[English]</a></p>

在“功能强大”的视野之外，还存在着另一种生命力：简单。

不是让某一个体为了强大而不断做复杂的事，而是让每个个体保持简单可靠，再把多个个体简单地组织起来，以简单的整体达到相同的最终目的。Simple ETL Spooler 就是这样一层简单到透明的存在。它不负责决定业务语义，而专注于承接已经声明好的数据搬运工作。

可以把每一个 Task 想象成一个亲和的人：左手牵着 EXTRACT，右手牵着 LOAD，自己专注于二者之间的透明适配。这样一来，左右两边的事情仍然交给最擅长它的人，并继续以各自最擅长的方式去做，各自所承受的局部复杂性自然被压得最低；而这双牵起的手，又把前后两端的差异与扰动进一步隔离住，阻断复杂性沿着整条传递链向外溢出。一个 Task 会被保存为清晰契约；多个 Task 会被编排成清晰脉络；整个过程也天然具备观察、排障与重放能力。

## 五分钟快速开始

先把它记成两个层级：

- 一个 Task 描述一次最小的搬运任务，并携带完整上下文
- 一个 Batch 把多个相关 Task 归为一组，并表达它们之间的编排及时序关系

最常见、也最基础的使用方式其实只有三步：

| `CREATE_BATCH` |  | `ADD_TASK` |  | `START_BATCH` |
|:---:|:---:|:---:|:---:|:---:|
| 创建批次 | ➔ | 加入任务 | ➔ | 启动执行 |

下面是一份最小但真实的例子：
```sql
DECLARE
    v_batch_id  SIMPLE_INTEGER;
BEGIN
    v_batch_id := {Schema}.UTIL_SYS_ETL.CREATE_BATCH(
        inComment        => 'Demo: sync data from source to target',
        inScheduled_Time => SYSDATE
    );
    {Schema}.UTIL_SYS_ETL.ADD_TASK(
        inBatch_ID         => v_batch_id,
        inSerially         => TRUE,
        inExtract_Type     => 'SQL',
        inExtract_Source   => 'SDBXYZ',
        inExtract_Command  => 'select PORT_CODE, MARKET_VALUE from SOME_SOURCE where AS_OF_DATE = :AS_OF_DATE',
        inExtract_Params   => '{"AS_OF_DATE":"2026-07-31"}',
        inLoad_Type        => 'SP',
        inField_Mapping    => '{"PORT_CODE":"in_PORT_CODE","MARKET_VALUE":"in_MARKET_VALUE"}',
        inMerge_Params     => '{}',
        inLoad_Destination => 'EDBXYZ',
        inLoad_Command     => 'SOME_TARGET_PACKAGE.LOAD_DATA',
        inTask_Comment     => 'Load latest market value snapshot'
    );
    {Schema}.UTIL_SYS_ETL.START_BATCH(v_batch_id);
    DBMS_OUTPUT.PUT_LINE(
        {Schema}.UTIL_SYS_ETL.WAIT_BATCH(
            inBatch_ID => v_batch_id,
            inTimeout_Minutes => 30
        )
    );
END;
/
```

> 注：文中的 `{Schema}` 指代你在部署本系统数据库组件时所选用的实际模式名。

这个示例已经足够说明最常见的调用方式；至于 `ADD_TASK` 如何承接参数适配与上下文拼装，会在后文再展开。而在实际项目里，上层应用往往还会再做一层面向场景的轻量封装，让调用进一步简化。

如果希望在调用端同步等待结果，可以补上：

- `{Schema}.UTIL_SYS_ETL.WAIT_BATCH`

如果需要对失败批次做重放，也可以使用：

- `{Schema}.UTIL_SYS_ETL.RERUN_BATCH`

看到这里，第一层需要记住的全貌其实只有一句话：

Task 负责连接 EXTRACT 与 LOAD，并在二者之间完成透明适配；Batch 和 `STEP_PLAN` 则把多个 Task 组织成直观结构。

## 为什么它会长成这样

### 贯穿始终的简单系统观

Simple ETL Spooler 不试图靠“什么都能做”来证明自己强大。恰恰相反，为了服务同一个最终业务目的，它反而尽力剥离不该属于自己的业务逻辑，让自己专注在更克制的边界之内。它把 边界清晰、动作简单、组合丰富 理解为另一种健康的系统观。这种“简单”不是对复杂问题的逃避，而是对复杂性的限缩：每个部分各安其位，只负责自己最适合负责的部分。

于是，在这套系统观里：

- 让最擅长 EXTRACT 的地方继续负责 EXTRACT
- 让最擅长 LOAD 的地方继续负责 LOAD
- 让 Simple ETL Spooler 专注于契约持久化、透明适配、批次编排与运行承接
- 让更上层的业务服务继续负责“为什么发生”与“哪些任务应该发生”

各部分继续以自己最顺手的方式工作，局部复杂性自然较低；清晰的边界又将这些复杂性封闭在原处，使系统整体保持简练。

在丛林里，个体越强，越容易生存；但在软件体系里，各子系统之间不应是竞争关系，而应是共生协同关系。在这里，某个部件是否全能不重要，重要的是复杂性是否被锁在恰当的地方。局部能力单薄，总能通过协同来弥补；真正致命的，是某些局部因错位而包揽过多，从而让复杂性失控外溢。前者表现浅显，通常只影响局部效益；后者潜伏隐蔽，却会像癌细胞扩散一样危害整个系统的生命力。

### Task 不是第三种大能力

每一个 Task 的执行，本质上都是先在源端触发 EXTRACT、接着在目的端触发 LOAD。它并不试图膨胀成第三个厚重强大的动作层。它做的，只是把两边连接起来，并在中间完成透明适配，让源端和目的端各自的擅长得以继续发挥。

单个 Task 的职责可以概括为四步：

1. 在源端触发 EXTRACT
2. 获得结果
3. 在源端结果与目的端契约之间完成适配
4. 触发目的端 LOAD

由于它只连接、不包揽，我们可以通过声明不同的 Type 与 Source / Destination 组合，轻量承接多种异构系统之间的搬运关系。目前系统支持的端侧矩阵如下：

| 搬运端侧 | 动作类型 | 端侧类型 |
|:---|:---|:---|
| 📤 **EXTRACT（源端）** | SQL、SP | Oracle、SQL Server、Snowflake |
|  | MDX | SSAS Cube、Adaptiv MemoryCube |
|  | REST | RESTful API URL |
| 📥 **LOAD（目的端）** | SP | Oracle、SQL Server、Snowflake |

这张矩阵同时说明了当前能力边界：EXTRACT 支持 SQL、SP、MDX 与 REST，而 LOAD 目前统一为 SP。这个边界让 Task 始终保持克制：它负责连接与适配，而不是膨胀成新的执行引擎。

其中，Snowflake 的存储过程调用需要使用 `CALL` 语法，例如 `CALL schema_a.sp_b(:param1, ...)`，而不能像 Oracle 与 SQL Server 那样只写存储过程名。Simple ETL Spooler 会把以单 `:` 为前缀的具名变量或具名参数，翻译成 Snowflake 驱动所需的位置绑定。

同一套描述字段在不同端侧生态中会承载不同技术含义：

| 动作类型 | Source / Destination | Command | Params |
|:---|:---|:---|:---|
| SQL / SP | 数据库实例或连接配置 | SQL 语句或存储过程 | 以 JSON 对象表达的变量或参数 |
| MDX | 连接字符串 | MDX 查询 | 不使用 |
| REST | RESTful API URL | HTTP Body / Payload | 以 JSON 对象表达的 HTTP Headers、Method 及其他请求元数据 |

所以，Task 不是第三种大能力，而是 EXTRACT 与 LOAD 之间的多态连接器。它利用一组克制而统一的描述字段（如 `_Source / _Destination`、`_Command`、`_Params`），在不同端侧之间维持一致的契约外形，而把具体差异收拢在内部适配层中。

这种透明适配，不只发生在源端与目的端之间，也体现在对上层暴露的 `ADD_TASK` 接口里。借助 `inExtract_Params`、`inField_Mapping` 与 `inMerge_Params` 这些极简字典，上层调用方不必再逐个处理绑定变量、字段对位，以及结果到目的端契约之间的细碎拼装。

### 解决的不是 what，而是 how

既然它的定位是透明适配与运行承接，它真正要解决的，不是业务上“发生了什么”，而是这些已经被定义好的动作应当“如何发生”。在这套分层里，Simple ETL Spooler 更适合回答的问题是：一份搬运契约，应当如何被保存为可执行表达；一个动作如何交给最擅长的端侧去完成；多个动作之间的关系又如何被显式组织、调度、观察和重放？

在运行组织这一面上，Simple ETL Spooler 更像一个尽责的邮递员。它并不关心某一封信里谈的究竟是什么业务、涉及哪些对象、为什么要在这一刻寄出；这些都属于写信人与收信人的世界。它关心的是另一组更低一层、也更通用的问题：这封信从哪里收、该送到哪里、途中如何封装与转交、多封信怎样按批次与路线组织，以及如何让投递全程可追溯、可回放。也因此，它的强项不是“理解业务”，而是甘当基础的搬运工与调度员，专门替更上层承接那些形式类似却又不完全重复、且必须被可靠解决的“如何发生”问题。

当然，what 与 how 并不是绝对概念。合理的系统分层，通常是层层递进：这一层所面对的 what，到了上一层，往往又属于它需要解决的 how。

像“职责专一”、“关注点分离”、“分层与解耦”这些原则，大概是软件人员熟悉得如同空气一样的简单道理。因为太过熟悉，它们很容易退化为概念、术语，甚至某种形式化的教条。而在交付压力持续累积、系统逐渐长大、需求不断涌入之后，人们容易倾向于选择能够最快见效的规划方向。这些压力所推动的方向，未必与系统内部自然的生长方向一致。很多时候，直接照着最终需求划出来的边界，与顺着内在性质形成的边界，恰恰彼此垂直。

如果一个餐馆后厨按照“一道菜”进行垂直包揽，让每位厨师不仅负责炒菜，还要亲自选购食材、洗菜备料、烹饪加工、端盘上菜，作为旁观者，看到一个厨师像邮递员一样频繁奔波于街巷之间，我们大概都会觉得这样的组织方式有些别扭。但从那一道菜的角度看，这些原则似乎又都能解释得通：职责专一，因为他只负责这一道菜；关注点分离，因为他不需要关心其他菜；分层与解耦，因为一盘菜与一桌菜之间同样存在边界。听起来甚至相当冠冕堂皇。

问题更常在于：复杂性未必来自原则缺失，而是边界被划向不对的方向。由于软件中的代价不像餐馆后厨那样直观可见，那些本应从业务主线中横向剥离出去的搬运、编排与运行职责，被糅合进同一个以最终业务划分的单元之中，往往既不会显得那么荒诞，甚至还能长期维持表面的合理与运转。因此，这些本应横向剥离的复杂性，需要由一个沿着更合适方向划定的边界来承接。

### 为什么需要这样一层

具体来说，这一层要集中处理的，是三类经常被糅合进业务主线的问题：

- **搬运动作混入业务主线**：上层应用在实现业务逻辑时，随处夹杂 EXTRACT 与 LOAD 这类较低层动作，使业务主线越来越模糊
- **编排关系藏进硬编码**：流程依赖与推进脉络散落在应用逻辑之中，逐渐变得难看清、难调整、难追踪
- **执行现场未被集中留存**：一旦失败，排障只能从各处零散痕迹中拼凑完整链路，既繁琐又不准确，也难以精确重放

可以把这一层的引入，想象成是把一杯浑浊的水装进玻璃瓶并静置分离。那些原本会沿着整条业务水流四处弥散的底层泥沙，也就是数据搬运细节、编排关系和执行现场，在这里被收进简明清晰的表达。于是，业务主线得以重新变得澄净；那些不可避免的复杂性，也在这里沉淀凝聚。

每一个 Task，就是这样一个透明胶囊。它不再只是一次转瞬即逝的动作，而是一份被完整留下的搬运契约。再进一步，通过 Batch 和 `STEP_PLAN`，这些胶囊之间的编排、先后顺序与执行状态，也被放上了托盘，呈现出明晰结构。Simple ETL Spooler 所做的，正是替更上层集中接住这些复杂性：任务执行、批次状态、时序编排，以及围绕它们展开的观察、排障与重放能力。而真正承担这件事的，正是下面要展开的三个核心抽象：Task、Batch 与 `STEP_PLAN`。

## 它究竟如何工作

### 核心抽象：Task、Batch、STEP_PLAN

#### Task：最小搬运契约（透明胶囊）

Task 不是一条转瞬即逝的执行命令，而是一份被保存下来的完整契约。在这个透明胶囊里，源端与目的端的连通信息、字段如何适配、运行时应携带哪些上下文，都会被一并收好。因此，它回答的并不只是“调一下某个动作”，而是把一次数据搬运所需的现场条件完整封装起来。

在这个胶囊内部，`FIELD_MAPPING` 扮演着最核心的透明适配角色。表面看，它只是一个映射配置；本质上，它是在源端结果形态与目的端输入契约之间，承担轻量而直接的转换职责。

| 源端结果 |  | 透明适配 |  | 目的端参数 |
|:---|:---:|:---|:---:|:---|
| **逐行对象数组**<br>`{ column: value, ... }[]` | **➔** | `FIELD_MAPPING` | **➔** | **具名数组参数**<br>`{ param: value[], ... }` |
|  |  | `MERGE_PARAMS` | **➔** | **附加单值参数**<br>`{ param: value, ... }` |
|  |  |  | **↓↓↓** | **特殊键 `"*"`**<br>`{ "*": "json_packet" }` |
|  |  |  |  | **`json_packet`** `=>`<br>`{`<br>&nbsp;&nbsp;`array_param: value[],`<br>&nbsp;&nbsp;`...,`<br>&nbsp;&nbsp;`scalar_param: value,`<br>&nbsp;&nbsp;`...`<br>`}` |

具体到 `FIELD_MAPPING`，适配处理会沿着以下路径展开：

- **天然一致时**：如果源端结果列名与目的端入参名本就一致，就不必额外声明，系统可直接完成关联绑定
- **局部差异时**：只需把少数例外显式写出，例如 `{"Market Value":"in_MARKET_VALUE"}`。像 `{"Unwant Column":null}` 这样的声明，也属于这一类局部差异的特例
- **源端多余列时**：绑定时会自动忽略目的端不需要的结果列，效果等同于将其映射为 `null` 或 `""`
- **源端缺少列时**：目的端未被源端结果提供的入参，会被视为缺省参数，交由目的端在运行时自行处理

更准确地说，源端结果首先表现为一组逐行对象；透明适配器会按目的端契约，将其逐项整理为一组等长数组参数，并再合并上 `MERGE_PARAMS` 指定的单值参数，形成最终输入目的端的全部参数；若存在重名部分，则以 `MERGE_PARAMS` 为准。

- **高度异构时**：当映射声明中指定特殊键 `*`（例如 `{"*":"json_packet"}`）时，透明适配器会在前述变换基础上，将最终参数整体再封装为一个 JSON，并以单一参数 `json_packet` 交给目的端处理。这个特别约定主要面向源端与目的端高度异构的场景：尤其当目的端本身是某类场景的通用接收器时，它无需受硬编码参数签名约束，而可以直接从 JSON 负载中解析其中承载的动态数据结构。对于 REST 类型的源端来说，这种做法尤为合适：其返回结果往往天然就是 JSON，而不是二维结果集，前述列名映射对它甚至无从施展；因此，原样 JSON 传递通常既最自然，也最具通用性。

目的端也因此可以继续按照自己最原生、最顺手的契约来接收数据，而不必为了迁就上游去扭曲自身接口。透明胶囊的意义，也正在于此：它把适配动作收进中间层，让源端与目的端都尽量保留各自原生的形态。

#### Batch：逻辑编排托盘

如果说 Task 是一个个透明胶囊，那么 Batch 就是承载这些胶囊的逻辑托盘。它自己并不负责实施具体的数据搬运，而是负责把服务于同一业务目的的多个相关 Task 收拢到同一个批次周期里。一旦被放进同一个托盘，这些 Task 的汇聚关系、推进进度以及整体成败，就不再只是彼此孤立的局部事件，而会被作为一个整体来控制与追踪。于是，调用方看到的就不只是“若干任务各自执行过没有”，而是“这一整盘任务现在处于什么状态、运行到了哪里、是否可以整体等待、整体重放”。

同时，Batch 还承担了一个很实用的时间入口。借助 `CREATE_BATCH` 时开放的 `inScheduled_Time`，调度方不仅可以决定这一盘胶囊如何组织，还可以决定它应在什么时刻被唤醒执行。于是，托盘不只承载空间上的编排，也承载时间上的运行安排。

在实践中，Batch 不只可以由外部应用创建，也可能在运行过程中，由前序某个 Task 的源端或目的端存储过程根据当时的数据状况动态派生出新的 Batch，形成批次级联；而 `CREATE_BATCH` 的可选参数 `inParent_Batch_ID`，则负责标记这类父子批次关系。

#### STEP_PLAN：直观的运行图

`STEP_PLAN` 的意义，不只是给任务排一个顺序号。它更重要的作用，是把任务之间的时序依赖直接表达在运行记录之中。

在同一个 Batch 托盘里，具有相同 `STEP_PLAN` 的任务属于同一个并行执行组；不同 `STEP_PLAN` 的组则按序推进。于是，“哪些可以一起跑，哪些必须等前一步完成再继续”，会直接显露在运行图表上。

| STEP_PLAN 1 |  | STEP_PLAN 2 |  | STEP_PLAN 3 |
|:---|:---:|:---|:---:|:---|
| Task A<br>Task B<br>Task C | ➔ | Task D<br>Task E | ➔ | Task F<br>Task G |

出了问题，看一眼这张运行图，就能知道当前卡在第几步、前后依赖是什么，可一下子定位到具体 Task 的源端或目的端；修复根因后，重放仍以整个 Batch 为单位。

### 把编排写进数据，而不是藏进代码

很多系统之所以越长越重，并不只是因为动作本身变多了，更常见的原因，是动作之间的关系被一重重藏进了硬编码里。哪些任务属于同一批、哪些必须先后推进、哪些可以并行、失败后应重发哪一段，这些本该被看见的编排信息，往往散落在应用逻辑、脚本分支、定时器配置，甚至重重嵌套的设计器界面之中。

Simple ETL Spooler 选择走另一条路：把编排本身也当作一种应被持久化的对象，直接写进简明的数据表达里。Task 负责声明单个搬运契约，Batch 负责组织相关 Task，`STEP_PLAN` 负责表达时序关系；于是，原本隐身在代码里的编排逻辑，就变成了简明的符号表达。这样做的价值，不只是在于“看起来更整齐”。编排脱离源码文本之后，理解一条任务链不必先翻阅多层代码，调整一次编排也不必总靠重新拼装过程分支。编排被写进简明的数据表达之后，任务链的运行组织便可一目了然。

这并不意味着代码不再重要。代码仍然负责完成真正的 EXTRACT 与 LOAD 动作，而编排留在表达关系的地方。二者边界越清楚，各自内部条理越清晰，系统整体就越容易维护。

### 先落盘契约，再驱动流水线

在很多业务实现里，动作往往被编进静态代码；可每一次的实际运行轨迹以及关键上下文，都只短暂停留在转瞬即逝的调用现场中，随着流程推进而消散。这样做并非不能完成任务，但一旦中途失败，想回头看清“刚才究竟做了什么”，常常要耗费很大精力。Simple ETL Spooler 选择把顺序倒过来：先把契约落盘，再让流水线启动。也就是说，先把 Task、Batch、`STEP_PLAN` 及其上下文保存为完整记录，再由运行层按既定编排推进执行。于是，执行不再是一次没有留痕的瞬时动作，而是对一份已落盘契约的实际兑现。

这个次序看似只是把“先存后跑”调了个顺序，本质上却决定了现场会不会留下清晰痕迹。契约一旦先被完整收录，后续的状态汇总、性能分析、审计、排障与重放，才都有了共同的锚点。调度方面对的，也不再是若干来去不明、难以回溯的调用现场，而是一组条理清晰、可以被反复引用与审视的运行记录。

从这个角度看，Simple ETL Spooler 并不是一条一边流动一边抹去脚印的输送带；它更像是一条先把包裹登记入册、再安排出仓路线的流水线。正因为每一次搬运在出发前就已经落盘为清晰契约，后续执行便能按照既定时序直接展开，也能在需要时回头核对完整现场。

### 让系统便于自我观察

当契约、编排与执行现场都被持续落盘之后，系统便更容易感知整体运行状态。它看到的，不再只是某一次调用有没有报错，而是某一批任务当前处于什么阶段、卡在第几步、哪些任务已经完成、哪些仍在等待、失败发生在整条链路的什么位置。继而，运行状态会直接叠加其上，形成面向全局的运行视图。

| STEP_PLAN 1 |  | STEP_PLAN 2 |  | STEP_PLAN 3 |
|:---|:---:|:---|:---:|:---|
| ✓ Task A<br>✓ Task B<br>✓ Task C | ➔ | ● Task D<br>✓ Task E | ➔ | ○ Task F<br>○ Task G |

这些状态会进一步落实为一组可查询、可追踪的状态流转，例如 `DRAFTING`、`READY_TO_RUN`、`RUNNING`、`COMPLETED` 与 `COMPLETED_WITH_ERROR`。

系统也因此可以随时回答：活儿现在干得怎么样了？

这使得系统在日常运行时更像一块真正有状态感的仪表盘，而不只是若干零散日志的堆积。排障时，不必再先到处打捞痕迹、再反向拼凑链路；调度时，也不必推测“现在大概跑到哪里了”。批次、步骤、状态与上下文都已摆在台面上，观察、定位与决策因此建立在同一份运行视图之上。

对日常排障和维护而言，系统直接暴露的这两个视图，就是最直接的观察入口：

- `{Schema}.VIEW_UTIL_SYS_ETL_BATCH_STATUS`：透视宏观托盘
- `{Schema}.VIEW_UTIL_SYS_ETL_TASK_STATUS`：透视微观胶囊

为了保持运行时引擎的轻量与响应速度，批次一旦完结，底层记录会被自动迁移至归档表；这两个视图则把“当前活跃表”与“历史归档表”整合起来，对外屏蔽冷热分离的存储细节。使用者无需自行拼接跨表 SQL，就能直接得到一致且完整的全周期记录。

常用查询如下：

```sql
SELECT * FROM {Schema}.VIEW_UTIL_SYS_ETL_BATCH_STATUS ORDER BY BATCH_ID DESC;
SELECT * FROM {Schema}.VIEW_UTIL_SYS_ETL_TASK_STATUS ORDER BY BATCH_ID DESC, STEP_PLAN, TASK_ID;
```

故障定位可以直接从这两个视图开始：先看 Batch 视图锁定批次，再看 Task 视图定位具体报错节点；若 `RUNTIME_ERROR` 以 “Extracting Error:” 或 “Loading Error:” 开头，便可快速判断问题发生在源端还是目的端，后续文字则是该端侧原样返回的错误信息。需要更丰富的诊断细节时，也应该尽量在相应端侧补充。修复问题之后，通常只需调用一句 `RERUN_BATCH`，整批任务便带回完整上下文，沿原有契约重新运行，方便反复调试和查验。

此外，后台引擎还会完整记录每个 Batch 的起止时间与各 Task 的完结时刻，使每一次运行节奏都自然沉淀为性能基线。当你需要优化搬运链路与并行排布，或回到源端 / 目的端继续排查慢点时，这些记录便会成为一份很务实的参照。这里也有一个刻意保留的架构折中：系统并不会为每个细分任务额外回写精确起跑时间，以免引入过多数据库寻址交互；这是在“运行时尽量轻量”与“事后追溯颗粒度更细”之间的一次有意识取舍。

Simple ETL Spooler 所提供的可观察性，并不止于回看发生过什么，更在于让运行中的全局态势始终可被掌握。对运行系统来说，这往往比事后的局部日志更有价值。

## 在你的企业环境中落地

到了这里你会发现，前文展开的大多是数据库中的契约、编排与状态记录；那么，究竟是谁在后台轮询队列、拉动时间线，并把这些契约执行起来？当前这套开源实现给出的答案，是一个用 C# 编写的 Windows Service 守护进程。

Spooler 这个名字本身并非偶然，它在角色上很像一个面向数据搬运场景的 Print Spooler：长驻后台，轮询待办队列，按各 Batch 的既定编排推进其下的 Tasks，并协调源端与目的端之间的交接与适配，再把执行结果与状态变化持续复写回数据库记录之中。于是，前文那套清晰契约与运行图表，才不只是被保存下来，更会被这层守护进程真正驱动起来。

这套开源代码已经把企业落地可能需要的改动集中起来，并以 `customize...` 注释标明相应的接入点，而环境差异和 Spooler 运行参数归配置管，其余部分不用动，也不用理会。

完成必要的定制后，用安装脚本部署主控数据库，再将编译好的 Windows Service 安装到指定节点并启动，Spooler 就连上主控数据库，开始持续承接队列中的批次任务。还可以将 Windows Service 部署到多个物理节点，连到同一个主控数据库；每个 Batch 作为整体只由其中一个节点拾取。

应用开发只需面对那几个简单的调用接口，无需触及诸如守护、轮询、执行推进与状态回写这些脏活累活。

目前已支持 Oracle、SQL Server、Snowflake、MDX 和 REST 等多种端侧类型，也可以通过局部扩展加入新的端侧类型，Snowflake 和 REST 就是后续加入的。主控数据库目前采用 Oracle，纯属当初顺手选择；若换成其他数据库平台，则需要相应修改数据库脚本和 Windows Service 代码。

无论是少量定制、扩展端侧类型、迁移主控数据库，还是根据不同场景重新选择运行机制，这些还都属于实现范畴；更值得被延续的，其实是背后关于边界、复杂性、透明适配与可观察性的思考。

## 它适合解决什么，不适合解决什么

说到底，Simple ETL Spooler 适合的，从来不是一切与数据有关的问题，而是一类边界相对清楚的问题：

- 搬运契约可以被清晰表达；
- 执行承接、时序组织、现场留存与后续运维可能构成不少负担。

因此，它尤其适合：

- 在多个异构系统之间反复执行形式相近的数据搬运任务；
- 将若干相关任务组织成批次，并明确表达串并行关系与推进顺序；
- 为执行现场留下完整痕迹，以支撑状态汇总、性能分析、审计、排障与重放；
- 让上层业务代码从大量底层 EXTRACT / LOAD 细节中抽身出来，只保留对“何时声明什么任务”的控制。

顾名思义，Simple ETL Spooler 更自然地服务于批量数据搬运，类似班次性运输。每一批出发前备好行程单，承运方按既定班次收发、照行程单集散转运。一批批任务由此共用同一套承运底座，遵循共同的运行节奏，优先照顾整体吞吐，而不是让每一项任务都随到随走，各自拥有一趟即时专车。

不同任务类型有不同的节奏要求。以低延迟事务为例，它更像随时待命的专车，优先照顾的是每次请求的即时响应与低时延；事件驱动、回调等机制可能会更自然地契合这类需求。

每一种机制各有自己的适用范围。不同问题的性质不可能都一样，自然也不必都用同一种方式解决。这些范围表明的是适用性，而非先进性。Simple ETL Spooler 不想让自己滑出边界，悄然变成一个包揽业务调度、规则处理甚至重型数据集成的全能中枢。

“哪个机制最厉害？”这种念头本身，就是不少问题的源头。真正值得探究的是：我们以什么样的系统性思考来作选择？如何分辨不同机制的自然边界？又如何让它们各尽所长、综合利用，使整个系统自全局而局部保持简单？

## 结语：仪表盘与生命力

虽然简单本身不会自动带来生命力，但复杂却时刻在暗中侵蚀生命力；一旦复杂失控，更可能是致命的。现实中的挑战，从来不是在简单与复杂之间二选一，而是在不断达成恰当目标的同时，不让问题以不恰当的方式复杂化。

趋向复杂化与扩张，远比克制与收束来得容易。无论是个人还是团队，我们都很容易在一次次局部合理的选择中，不知不觉地模糊边界、揽宽职责，把原本应当剥离的东西重新糅合回去。而在这个过程中，表面上甚至未必看得出哪里出了问题。因此，追求简单从来不是一句口号。它需要持续照见自身，从而看清自己在逐渐变成什么，并跳出标签迷局；一旦失去这种自觉，复杂性便会迅速扩张泛滥。

但光有这种内在自觉还不够，还需要清晰的外在证据链，尤其是在面对层出不穷的技术时髦与纷繁复杂的架构叙事时。在这个系统中，全程透视、性能记录与完整上下文留存，正是这套搬运流水线上的仪表盘；而仪表盘上摆动的指针，不也在帮助我们戳破那些貌似高级、甚至盲从内化的认知迷思吗？

一辆车即使没有仪表盘，依然可以轰鸣上路；一个人即使缺乏自省的习惯，同样可以每天吃喝劳作，甚至可能因为自我审视少了，对外说教的声音反而愈发高亢，愈显冠冕堂皇。但长期的黑盒狂奔，奔向的却是自我消耗。

这恰恰是 Simple ETL Spooler 试图避开的归宿。它之所以如此守护着“简单落盘、可视依赖、全程留痕”，正是希望整个数据流转系统始终保有这种“自省力”：让每一次动作都轮廓鲜明，让每一个故障都现场清晰而易于修复。

这种能够持续照见自身的简单，是稳健生命力的重要源泉。
